01

Calculator Overview

What it does

The project is a modular-arithmetic teaching calculator. It exposes GCD, extended GCD, modular inverse, modular addition, modular multiplication, and modular exponentiation.

For each operation, the Streamlit UI runs a manual implementation and a prebuilt implementation separately, measures each call with time.perf_counter(), and presents the result or error in two columns. Modular exponentiation additionally displays the hand-written square-and-multiply result.

Input and output flow

  1. The user selects an operation from the sidebar.
  2. The form renders only the fields needed for that operation.
  3. parse_int() trims input and accepts decimal or 0x-prefixed hexadecimal.
  4. The selected renderer calls both approaches through safe_call().
  5. Results, errors, and elapsed seconds are rendered side by side.
Important scope distinction The source contains two front ends: the Streamlit interface in calculatorUi.py and a command-line calculator/demo path in cpython.py. The algorithms are shared, but their presentation and error-handling flows differ.
02

Algorithms Used

The following descriptions separate algorithms explicitly written in the source from library calls whose internals are not defined by this project.

Binary long division by shift and subtract manual_mod(x, m)

Purpose: Compute a remainder without using Python’s %, //, or divmod() for the remainder itself. It is the reduction primitive used by the manual modular operations.

How it is used: gcd_naive(), mod_add_naive(), mod_mul_naive(), mod_pow_naive(), mod_pow_square_and_multiply(), and mod_inverse_naive() all depend on it directly or indirectly.

  1. Reject a zero modulus, then work with absolute values.
  2. Align the modulus with the highest bit of the absolute dividend using a left shift.
  3. Scan shifts from high to low. If the aligned divisor fits, subtract it.
  4. Convert a negative input back to Python’s non-negative remainder convention for a positive modulus.

Example: For 29 mod 6, align 6 << 2 = 24, subtract to get 5, then lower shifts no longer fit. The result is 5.

Data structures: Only integer scalars are used: the remainder, shifted divisor, shift counter, and sign flags. There is no array, table, graph, or heap.

Best timeO(1)
Average timeO(L)
Worst timeO(L)
SpaceO(1)

Here L is the relevant bit length. The best case occurs when the absolute dividend is smaller than the modulus, so no scan is needed. The loop has one pass per bit alignment in the general case. These are arithmetic-step bounds; actual Python big-integer operations also have costs dependent on operand size.

Binary shift-and-add multiplication naive_multiply(a, b)

Purpose: Multiply integers without using Python’s * for the main product.

  1. Record whether exactly one operand is negative and then use absolute values.
  2. Inspect the lowest bit of the multiplier. If it is one, add the current multiplicand to the result.
  3. Double the multiplicand with a left shift and halve the multiplier with a right shift.
  4. Repeat until the multiplier is zero, then restore the sign.

Example: 13 × 6 examines multiplier bits 0, 1, 1. It adds shifted multiplicands 0 + 26 + 52 = 78.

Data structures: Integer scalars only. The binary representation is accessed through bit operations rather than stored in a list.

Best timeO(1)
Average timeO(B)
Worst timeO(B)
SpaceO(1)

B is the bit length of the multiplier. A zero or one-bit multiplier ends immediately; otherwise there is one loop iteration per multiplier bit. The integer values grow during shifts, so bit-level memory is proportional to operand/result size even though the number of named variables is constant.

Euclidean algorithm for GCD gcd_naive(a, b)

Purpose: Find the greatest common divisor of two integers.

  1. Replace both inputs with their absolute values.
  2. While the second value is nonzero, replace the pair (a, b) with (b, a mod b).
  3. Return the final nonzero value.

Example: gcd(48, 18) becomes (18, 12), (12, 6), then (6, 0); the answer is 6.

The remainder is supplied by the project’s shift-and-subtract manual_mod(), so this is not a call to Python’s built-in modulo in the manual path.

Best timeO(1)
Average timeO(log N)
Worst timeO(log N)
SpaceO(1)

N = min(|a|, |b|) at the algorithmic level. The best case is when the second input is zero or the first remainder is zero. Euclidean remainders shrink quickly, with a logarithmic worst-case number of iterations. Each iteration also pays for manual_mod(); a full bit-complexity analysis must account for the size of those integer operations.

Iterative extended Euclidean algorithm extended_gcd_naive(a, b)

Purpose: Return (g, x, y) such that a*x + b*y = g, where g = gcd(a, b). The coefficients are needed for modular inverses.

  1. Separate signs and run the recurrence on absolute values.
  2. Maintain remainder pairs (old_r, r) and coefficient pairs (old_s, s), (old_t, t).
  3. Compute the quotient q = old_r // r.
  4. Update each pair using the same recurrence: new value = old value minus q times current value.
  5. When r reaches zero, restore input signs and return the final gcd and coefficients.

Example: For 35 and 15, one valid result is (5, 1, -2), because 35(1) + 15(-2) = 5.

Data structures: Six integer state variables, not a table of all divisions. The implementation is iterative, so it does not consume recursion-stack space.

Best timeO(1)
Average timeO(log N)
Worst timeO(log N)
SpaceO(1)

The iteration count follows Euclid’s algorithm. Coefficients may become large, so the storage occupied by the integer objects grows with input size; O(1) describes the number of scalar state slots, not a constant number of machine words.

Modular inverse via extended GCD mod_inverse_naive(a, m)

Purpose: Find x with a*x ≡ 1 (mod m).

  1. Require a positive modulus.
  2. Reduce a with manual_mod().
  3. Run extended_gcd_naive(a_mod, m).
  4. Accept the coefficient only when the gcd is one; otherwise report that no inverse exists.
  5. Reduce the coefficient into the range determined by the modulus.

Example: The inverse of 3 mod 7 is 5, because 3 × 5 = 15 ≡ 1 mod 7.

Best timeO(1)
Average timeO(log m)
Worst timeO(log m)
SpaceO(1)

The dominant work is extended GCD; the final reductions add another linear-in-bit-length manual remainder scan. An inverse exists exactly when gcd(a, m) = 1.

Modular addition and modular multiplication mod_add_naive() / mod_mul_naive()

Addition: Compute a + b, then reduce with manual_mod(). At the loop level this is one addition plus one remainder operation.

Multiplication: Compute the product with naive_multiply(), then reduce it with manual_mod(). This deliberately exposes the lower-level binary multiplication technique.

Add bestO(1)
Add worstO(L)
Multiply bestO(1)
Multiply worstO(B + L)

At the source-level arithmetic-step model, addition is dominated by the manual remainder scan over bit length L; multiplication is dominated by B shift-and-add steps plus the reduction. Both use only integer scalars.

Repeated modular multiplication mod_pow_naive(base, exp, mod)

Purpose: Compute base^exp mod mod in the most direct way shown in the project.

  1. Reject negative exponents.
  2. Initialize result = 1 mod mod and reduce the base.
  3. Repeat exactly exp times: multiply the running result by the reduced base and reduce again.
  4. Return the final remainder.

Example: 2^5 mod 7 performs five modular multiplications and returns 4.

Best timeO(1)
Average timeO(E)
Worst timeO(E)
SpaceO(1)

E is the exponent. The actual cost is approximately E calls to the manual multiply-and-reduce path, so bit length makes each iteration more expensive. In the provided source, NAIVE_EXP_LIMIT = None, meaning no safety cap is active in the Streamlit path.

Square-and-multiply exponentiation mod_pow_square_and_multiply()

Purpose: Compute modular powers in logarithmic exponent steps without using built-in pow(). The UI labels it a bonus and the source calls it “not naive, not library.”

  1. Initialize result to 1 mod mod, reduce the base, and copy the exponent to e.
  2. If the least-significant bit of e is one, multiply the result by the current base.
  3. Square the current base modulo mod.
  4. Shift e right by one bit and continue until it is zero.

Example: The binary representation of 13 is 1101, so the algorithm processes four bits rather than performing thirteen multiplications.

Best timeO(1)
Average timeO(log E)
Worst timeO(log E)
SpaceO(1)

There is one loop per exponent bit. Each bit may cause one multiply and every iteration causes one square, with manual multiplication and remainder underneath.

Comparison and validation techniques run_both() / run_correctness_tests()

Separate timing: run_both() calls the manual function, catches its exception, times it, then calls the prebuilt function and times it independently. It compares values only when both calls succeed.

Randomized validation: run_correctness_tests() generates random inputs with random.randint(), checks GCD and Bézout identities, verifies modular inverses, and compares modular arithmetic against Python’s result. Exponentiation receives 200 smaller random tests.

Data structures: Tuples carry argument groups and extended-GCD results; local scalar variables carry timings and errors. The test suite does not build a persistent dataset.

One comparisonO(T)
Test suiteO(K · T)
Extra spaceO(1)
Timing cost2 calls

T is the cost of the selected operation and K is the number of trials. The test suite is a development/demo feature, not part of the Streamlit request path.

04

Alternative Algorithms

Remainder and GCD

Alternative: A binary GCD (Stein’s algorithm) replaces division/remainder with shifts, subtraction, and removal of powers of two. It is often useful when division is expensive.

Comparison: The current Euclidean algorithm is shorter and conventional. Binary GCD has O(log N) arithmetic iterations and O(1) auxiliary space, but can require more subtraction steps and is not automatically faster for Python big integers.

Prefer it when: the environment makes division especially costly or a bit-oriented implementation is the teaching objective.

Extended GCD and inverse

Alternative: Lehmer’s extended GCD uses leading digit/word approximations to reduce the number of full big-integer divisions. For a prime modulus, Fermat’s theorem can compute an inverse as a^(m-2) mod m, provided a is nonzero modulo the prime.

Comparison: Extended GCD works for every positive modulus when the gcd is one; Fermat’s route is restricted to prime moduli and adds exponentiation work. Lehmer’s method can improve large-integer performance but is more complex.

Prefer it when: inputs are very large and prime-modulus assumptions or a mature big-integer library are acceptable.

Multiplication and modular reduction

Alternatives: Python’s built-in multiplication, Karatsuba/Toom-Cook multiplication, and Montgomery or Barrett reduction.

Comparison: The current code intentionally exposes shift-and-add. Built-in big integers use optimized internals; Montgomery reduction is especially useful when many multiplications share an odd modulus, while Barrett reduction avoids repeated division using a precomputed reciprocal.

Complexity: Karatsuba is commonly described as O(Llog23) for L-bit operands; exact built-in and library behavior is implementation-dependent. Montgomery and Barrett have costs tied to big-integer multiplication and are most valuable in repeated modular workloads.

Exponentiation

Alternative: The project already includes square-and-multiply. Other alternatives include a left-to-right or right-to-left binary variant, sliding-window exponentiation, and a library modular-power routine.

Comparison: Repeated multiplication is O(E) modular products; binary exponentiation is O(log E); sliding windows reduce multiplications further by precomputing small odd powers, at the cost of O(2w) or similar window-dependent storage.

Prefer it when: exponents are large. The current square-and-multiply is the best fit here because it improves asymptotic behavior without adding a table or external dependency.

No invented alternative for opaque internals The source does not expose the internal algorithm of math.gcd(), gmpy2.gcdext(), Python’s pow(), or the integer multiplication and modulo operators. Their alternatives above are conceptual choices, not claims about what those APIs currently do internally.
05

Benefits of the Current Algorithms

Teaching clarity

The code makes the mechanics visible. Bit shifts, remainder reduction, quotient updates, and exponent-bit inspection can be traced directly, then compared with a production-oriented implementation.

Small memory footprint

The manual paths use scalar state and loops rather than storing a history of steps. Their auxiliary space is constant in the number of variables, which is appropriate for an interactive calculator.

Useful performance contrast

Running both routes with independent timers turns the calculator into a small experiment. The O(E) naive exponentiation makes the advantage of logarithmic exponentiation easy to observe.

Maintainable separation

Each operation has a named manual function, a prebuilt counterpart, and a UI renderer. That separation makes correctness comparisons and future substitutions straightforward.

Scalable enough for the lab

The core routines accept Python arbitrary-precision integers and the demo intentionally includes 512-bit values. They are suitable for moderate educational inputs, though the naive power path is not a production cryptography primitive.

Appropriate, not universally superior

The manual algorithms are appropriate because the project’s goal includes learning and comparison. For high-throughput or security-sensitive work, optimized, audited libraries are preferable to these instructional implementations.

def mod_pow_square_and_multiply(base, exp, mod):
    result = manual_mod(1, mod)
    b = manual_mod(base, mod)
    e = exp
    while e > 0:
        if e & 1:
            result = manual_mod(naive_multiply(result, b), mod)
        b = manual_mod(naive_multiply(b, b), mod)
        e >>= 1
    return result
09

Overall Analysis

Most important algorithms

The central chain is manual remainder reduction, Euclidean GCD, extended Euclid for coefficients and inverses, and modular exponentiation. Square-and-multiply is the most important performance improvement because it changes exponentiation from linear in the exponent to logarithmic in the exponent.

Why they fit

They are compact, understandable, use little auxiliary memory, support arbitrary-precision Python integers, and create a meaningful side-by-side comparison with the prebuilt routes.

Potential improvements

Enable a real exponent safety limit or default the UI to square-and-multiply for large exponents. Add a visible “results match” indicator, validate that moduli are positive before every modular operation, and handle missing gmpy2 with a clear dependency message.

Performance optimizations

Use built-in or audited big-integer operations for production workloads, reduce duplicate work when only one result is needed, and benchmark with multiple input sizes rather than one timing sample. For repeated large modular powers, consider Montgomery reduction or a sliding window.

Concrete source issue in the CLI path In calculator(), the expression if exp > NAIVE_EXP_LIMIT: compares an integer with None, but the supplied constant is NAIVE_EXP_LIMIT = None. In Python this raises TypeError after option 6 completes. The Streamlit UI does not execute this comparison, but the CLI path should guard it with NAIVE_EXP_LIMIT is not None and exp > NAIVE_EXP_LIMIT.
Would changing the algorithm matter? For small classroom inputs, the visible difference may be negligible and the current manual code is valuable precisely because it is inspectable. For large exponents, changing from repeated multiplication to square-and-multiply is a meaningful improvement. For production-scale or security-sensitive arithmetic, replacing the instructional manual routines with mature, audited implementations is more important than micro-optimizing these loops.

Accuracy note: This page documents behavior present in cpython.py and calculatorUi.py. Where a built-in, external library, Python runtime, or Streamlit internals are opaque, the documentation says so instead of assigning an unverified implementation.
